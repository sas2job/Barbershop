# ADR-0002: публичный HTTP-контракт бронирования

## Статус

Принято.

## Контекст

Первый вертикальный срез бронирования уже работает как HTML-сценарий:
клиент получает доступ к записи по `public_token`, а создание, отмена и
перенос выполняются через формы и редиректы. При этом в учебном плане API
упоминается как следующий этап. Нельзя считать HTML-маршруты JSON API без
явного контракта и тестов.

## Решение

- Зафиксировать текущий публичный HTTP-контракт в
  `docs/api/booking-web.openapi.yaml`.
- Считать контрактом публичные маршруты, параметры формы, статусы ответов и
  правило доступа по случайному токену.
- Сохранить HTML как текущий транспорт; JSON API добавлять отдельной версией
  и отдельным решением, если это потребуется интерфейсу или интеграциям.
- Считать атомарность переноса и сохранение старой записи при занятом новом
  слоте доменными инвариантами, которые проверяются интеграционными тестами.

## Последствия

Контракт можно проверять независимо от реализации представлений, а будущий
JSON API не будет случайно смешан с существующим клиентским сценарием.
OpenAPI-файл пока не подключён к генератору или CI-валидатору; это отдельная
задача, когда появится API-инструментарий.

## Проверка

`test/controllers/bookings_controller_test.rb` проверяет создание с редиректом
по токену, недоступность последовательного ID, отмену без удаления и
атомарный перенос.
