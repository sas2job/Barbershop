# Модуль 0: первый эксперимент с контекстом

## Вход от пользователя

Пользователь описал продукт своими словами:

> Пользователь заходит на сайт с десктопа или мобильного браузера и выбирает дату, время и стрижку (мужскую или женскую). Расписанием управляет администратор. Должен быть базовый функционал: записаться, посмотреть запись и редактировать запись администратором.

## Что известно явно

- Продукт является веб-приложением.
- Интерфейс должен работать на мобильных и десктопных экранах.
- Основной пользовательский сценарий — запись на услугу.
- При записи выбираются дата, время и вид стрижки.
- Изначально есть два вида услуги: мужская и женская стрижка.
- Расписанием управляет администратор.
- Пользователь может просмотреть созданную запись.
- Администратор может редактировать запись.

## Что AI не должен выдавать за требования пользователя

Из исходного описания нельзя заключить, что:

- пользователь обязательно создаёт аккаунт;
- клиент выбирает конкретного мастера;
- запись требует подтверждения;
- клиент может отменить или перенести запись;
- в салоне только один мастер;
- приложение принимает оплату;
- уведомления отправляются по email, SMS или через мессенджер;
- мужская и женская стрижки имеют конкретную стоимость или длительность.

Если AI добавляет это в проект без явной маркировки, он смешивает требования с собственными предположениями.

## Улучшенный контекст

### Цель

Создать адаптивное Rails-приложение для онлайн-записи на стрижку через мобильный или десктопный браузер.

### Роли

- Клиент создаёт и просматривает запись.
- Администратор управляет расписанием и редактирует записи.

### Основной сценарий

1. Клиент открывает сайт.
2. Выбирает мужскую или женскую стрижку.
3. Выбирает доступную дату и время.
4. Указывает необходимые контактные данные.
5. Создаёт запись.
6. Получает возможность посмотреть запись.

### Ограничения первой версии

- Только веб-интерфейс.
- Обязательна адаптация под мобильный и десктопный браузер.
- Только базовое бронирование и административное управление.
- Неопределённые продуктовые решения нельзя подменять предположениями.

## Нерешённые вопросы

Перед проектированием данных необходимо определить:

1. Есть ли временное ограничение на самостоятельную отмену или перенос?

## Уточнение контекста

После первого раунда вопросов пользователь принял решения:

- клиент выбирает только время, конкретный мастер может измениться;
- клиент не создаёт аккаунт;
- при записи клиент указывает имя и телефон;
- необходимость отдельного уникального кода пока не определена.
- клиент может самостоятельно отменить запись или выбрать другое время.
- запись подтверждается сразу после успешного создания и не требует одобрения администратора.
- клиент получает доступ к записи по защищённой ссылке со случайным токеном.

### Архитектурные следствия

- Назначение мастера является отдельной частью записи, управляемой администратором.
- Идентичность мастера не должна входить в неизменяемое клиентское обещание.
- Смена мастера не должна менять публичный идентификатор записи.
- Имя не является идентификатором пользователя.
- Телефон является контактными и персональными данными, но сам по себе не доказывает право просматривать запись.
- Публичный последовательный ID нельзя использовать как единственную защиту страницы записи.
- Перенос является составной бизнес-операцией: создать новую запись и аннулировать прежнюю.
- Обе части переноса должны быть атомарны.
- Новый слот проверяется повторно внутри транзакции, потому что после отображения свободных слотов его мог занять другой клиент.
- Если резервирование нового слота не удалось, исходная запись остаётся действующей.
- Отменённую запись следует сохранять для истории и освободить занимаемый ею слот.
- Состояние ожидания подтверждения не нужно; успешное создание записи означает резервирование времени.

### Принятое решение о доступе

После бронирования система выдаёт случайный непредсказуемый токен. Страница записи открывается только по ссылке с этим токеном. По ней клиент может просмотреть, отменить или перенести запись. Имя, телефон и последовательный ID не предоставляют доступ.

## Результат первого упражнения

Короткое исходное описание было преобразовано в инженерный контекст без незаметной подмены требований предположениями. Были явно разделены:

- факты, сообщённые пользователем;
- вопросы, требующие продуктового решения;
- архитектурные следствия требований;
- безопасные технические предложения;
- окончательно принятые решения.

## Checkpoint: AGENTS.md

### Ответ учащегося

> AGENTS.md содержит правила и style guide, по которым работает агент; они не должны быть привязаны к плану развития проекта.

### Уточнение

Ответ верный по главной идее: изменчивый roadmap не следует помещать в постоянные инструкции агента.

`AGENTS.md` может содержать не только правила стиля, но также:

- устойчивый рабочий процесс;
- команды запуска и проверки;
- правила безопасности;
- архитектурные ограничения;
- важные инварианты проекта;
- ссылки на источники подробных требований.

Подробный план, история решений и изменчивые требования хранятся в специализированных документах. Это сохраняет инструкции краткими и уменьшает постоянный расход контекстного окна.

## Checkpoint: model, agent, harness и tool

### Вопрос

Почему ошибка `git init` из-за read-only `.git` не была ошибкой модели?

### Ответ учащегося

> Потому что это событие должно совершаться явно пользователем и оно вносит изменения в файловую систему.

### Уточнение

Ответ правильно связывает ситуацию с разрешениями, но не каждое изменение файловой системы требует подтверждения. Агент может изменять файлы внутри заранее разрешённой рабочей области.

В этом случае:

- модель предложила допустимое действие — инициализировать Git;
- агент выбрал и вызвал shell tool;
- tool попытался выполнить `git init`;
- harness применил sandbox policy;
- специальная директория `.git` не была доступна для записи;
- после явного разрешения команда была повторена с расширенными полномочиями.

Следовательно, первоначальный сбой был ограничением среды исполнения, а не ошибкой рассуждения модели. Модель могла бы ошибиться позже, если бы неверно диагностировала причину или предложила небезопасный способ обхода ограничения.

## Checkpoint: планирование и исполнение

### Задание

Сформулировать проверяемые критерии готовности начального Rails-приложения до запуска генератора.

### Ответ учащегося

> В консоли можно создать расписание. Пользователь в консоли может получить расписание, выбрать дату и записаться.

### Разбор

Ответ описывает наблюдаемое поведение и поэтому полезен как основа acceptance criteria. При этом он относится не к техническому каркасу, а к первому вертикальному срезу бизнес-логики.

Работу следует разделить на два результата.

#### Технический каркас

- Rails-приложение загружается без ошибки.
- PostgreSQL development/test базы создаются и доступны.
- Стандартный тестовый набор запускается.

#### Первый вертикальный срез

- Администратор может создать услугу и рабочее расписание через Rails console.
- Для услуги и даты можно получить список свободных времён.
- Клиент может указать имя и телефон и забронировать свободное время.
- Успешная запись сразу имеет подтверждённое состояние и публичный токен.
- Повторное бронирование занятого времени отклоняется.

Rails console здесь выступает временным интерфейсом для проверки доменной логики. Реальный конечный пользователь позже будет выполнять тот же сценарий через браузер.

## Вывод об engineering context

Хороший контекст содержит не только описание желаемого результата, но и:

- явно известные факты;
- границы первой версии;
- роли и основной сценарий;
- ограничения;
- открытые вопросы;
- маркированные предположения.

Такой формат уменьшает вероятность того, что агент незаметно примет продуктовое решение за пользователя.
