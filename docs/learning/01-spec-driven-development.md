# Модуль 1: первый Spec Driven Development цикл

## Задача

Реализовать каталог услуг, который станет основой расчёта свободных слотов и записи клиента.

## Последовательность

1. Из предоставленного прайса выбраны услуги.
2. Требования отделены от предположений о длительности.
3. Создана спецификация `docs/specifications/001-service-catalog.md`.
4. Спецификация прочитана и принята пользователем.
5. Acceptance criteria переведены в восемь model tests.
6. Первый корректный RED-запуск дал восемь ошибок `uninitialized constant Service`.
7. Добавлены минимальная модель и миграция.
8. Тот же набор тестов стал GREEN: 8 tests, 18 assertions.
9. Выполнены RuboCop и Brakeman.
10. Пользователь вручную проверил сценарий через Rails console.

## Ручная проверка

В development-базе создана услуга:

```ruby
Service.create!(
  name: "Стрижка под машинку",
  category: :men,
  duration_minutes: 30,
  price_from_cents: 45_000,
  price_to_cents: 45_000
)
```

Запрос:

```ruby
Service.available_for_booking.in_category(:men).pluck(:name)
```

вернул:

```ruby
["Стрижка под машинку"]
```

SQL log подтвердил:

- открытие и успешный `COMMIT` транзакции;
- запись категории `men`;
- применение условий `active = TRUE` и `category = 'men'`.

## Ручная проверка отрицательного сценария

Пользователь попытался создать услугу, у которой максимальная цена меньше минимальной:

```ruby
Service.create!(
  name: "Некорректная услуга",
  category: :men,
  duration_minutes: 30,
  price_from_cents: 45_000,
  price_to_cents: 40_000
)
```

Rails вернул:

```text
ActiveRecord::RecordInvalid:
Validation failed: Price to cents must be greater than or equal to the minimum price
```

Некорректный объект был остановлен Rails validation до выполнения `INSERT`. Использование `create!` превратило ошибку в исключение; `create` вернул бы несохранённый объект с заполненным `errors`.

## Уровни верификации

- Спецификация отвечает на вопрос «что требуется».
- Автоматические тесты проверяют повторяемое поведение.
- Rails validations дают понятные ошибки до записи в базу.
- PostgreSQL constraints защищают данные при обходе модели и конкурентных операциях.
- Ручной сценарий подтверждает, что публичный способ использования работает так, как ожидает человек.
- Lint и security scan проверяют отдельные классы дефектов, но не доказывают бизнес-корректность.

## Важный вывод

Один успешный сигнал недостаточен. Уверенность появляется из нескольких независимых доказательств, каждое из которых проверяет свой тип ошибки.
