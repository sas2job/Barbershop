# Модуль 5: API и интерфейс

## Первый вертикальный срез

Добавлен JSON endpoint `GET /api/v1/availability`. Он возвращает доступные
часовые слоты для активной услуги и выбранной даты.

Ответ содержит `service_id`, нормализованную дату и массив ISO 8601 timestamp:

```json
{
  "service_id": 1,
  "date": "2026-09-05",
  "slots": ["2026-09-05T09:00:00+03:00"]
}
```

## Архитектурное решение

Контроллер API вызывает существующий `Availability::FindSlots`, поэтому HTML
и JSON используют один расчёт доступности. Бизнес-правила не дублируются в
клиенте или транспортном слое.

Версия endpoint указана в URL (`/api/v1`), чтобы будущие изменения формата
ответа не ломали текущий интерфейс. Клиентский аккаунт для получения слотов
не нужен.

## Проверка

- активная услуга возвращает рассчитанные свободные слоты;
- неактивная услуга отвечает `404`;
- некорректная дата отвечает `422` с JSON-ошибкой;
- интеграционные тесты: 3 теста, 8 assertions.

Контракт описан в `docs/api/booking-web.openapi.yaml`, поведение предметной
области — в `docs/specifications/003-availability-api.md`.

## Второй вертикальный срез

Добавлен `POST /api/v1/bookings`. API вызывает `Appointments::Book` и поэтому
сохраняет общие с HTML-сценарием правила: слот резервируется транзакционно,
запись сразу получает статус `confirmed`, а конкурентное занятие возвращает
`422`.

Успешный ответ имеет статус `201` и содержит публичный токен, статус, услугу и
время. Последовательный ID записи и клиентские данные в ответ не включаются.

## Проверка

- создание записи возвращает `201` и непредсказуемый публичный токен;
- занятый слот возвращает `422` без создания новой записи;
- интеграционные API-тесты: 5 тестов, 21 assertion.

## Третий вертикальный срез

Добавлены просмотр и отмена записи по публичному токену:
`GET /api/v1/bookings/:public_token` и
`DELETE /api/v1/bookings/:public_token`. API возвращает только данные,
необходимые для экрана записи, без имени и телефона клиента. Отмена меняет
статус и сохраняет историю.

Интеграционные тесты проверяют доступ по токену, отсутствие персональных
данных в ответе и отмену без удаления записи.

## Четвёртый вертикальный срез

Добавлен `PATCH /api/v1/bookings/:public_token` для переноса записи. Логика
вынесена в `Appointments::Reschedule`: при успехе новая запись создаётся, а
старая аннулируется атомарно; при занятом слоте исходная запись сохраняется.

## Следующий шаг

## Пятый вертикальный срез

Форма бронирования подключена к `GET /api/v1/availability`: при изменении
даты список часов обновляется без перезагрузки страницы. Серверный список
остаётся начальным значением, поэтому сценарий сохраняет работоспособность
при отключённом JavaScript.

Дата из date-picker синхронизируется со скрытым полем формы, поэтому после
динамического обновления слотов сервер получает ту же дату, которую видит
пользователь.

Для форматирования времени используется часовой пояс салона `Europe/Moscow`.

Добавить API-срез создания записи либо подключить endpoint к динамическому
обновлению слотов в существующей форме бронирования. Выбор следующего среза
нужно согласовать с потребностями интерфейса, а не считать JSON API самоцелью.
