# Модуль 5: API и интерфейс

## Первый вертикальный срез

Добавлен JSON endpoint `GET /api/v1/availability`. Он возвращает доступные
часовые слоты для активной услуги и выбранной даты.

Ответ содержит `service_id`, нормализованную дату и массив ISO 8601 timestamp:

```json
{
  "service_id": 1,
  "date": "2026-09-05",
  "slots": ["2026-09-05T09:00:00+03:00"]
}
```

## Архитектурное решение

Контроллер API вызывает существующий `Availability::FindSlots`, поэтому HTML
и JSON используют один расчёт доступности. Бизнес-правила не дублируются в
клиенте или транспортном слое.

Версия endpoint указана в URL (`/api/v1`), чтобы будущие изменения формата
ответа не ломали текущий интерфейс. Клиентский аккаунт для получения слотов
не нужен.

## Проверка

- активная услуга возвращает рассчитанные свободные слоты;
- неактивная услуга отвечает `404`;
- некорректная дата отвечает `422` с JSON-ошибкой;
- интеграционные тесты: 3 теста, 8 assertions.

Контракт описан в `docs/api/booking-web.openapi.yaml`, поведение предметной
области — в `docs/specifications/003-availability-api.md`.

## Следующий шаг

Добавить API-срез создания записи либо подключить endpoint к динамическому
обновлению слотов в существующей форме бронирования. Выбор следующего среза
нужно согласовать с потребностями интерфейса, а не считать JSON API самоцелью.
