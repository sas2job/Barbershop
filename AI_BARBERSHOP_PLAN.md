# Барбершоп на Ruby on Rails: изучение AI-разработки на практике

## Цель маршрута

Создать полноценное приложение барбершопа на актуальных Ruby и Ruby on Rails и на каждом этапе осознанно изучить концепции из программы Hexlet «ИИ для разработчиков».

Барбершоп — сквозной учебный проект, а не просто итоговое домашнее задание. Цель считается достигнутой только при выполнении двух условий:

1. Приложение работает, протестировано и развёрнуто.
2. Каждую использованную AI-концепцию можно объяснить, воспроизвести и применить в другой задаче.

Маршрут не привязан к четырём неделям. Переход к следующему модулю происходит после проверки результата и понимания текущего.

## Как будем учиться

Каждый модуль проходит по одному циклу:

```text
Теория → небольшой эксперимент → применение в проекте
       → проверка результата → разбор ошибок → фиксация знаний
```

Для каждого модуля сохраняются:

- реализованная часть приложения;
- спецификация или инженерный документ;
- команды и тесты, доказывающие работоспособность;
- краткая запись «что изучено»;
- примеры удачных и неудачных запросов к агенту;
- ответы на контрольные вопросы.

AI не заменяет понимание. Сообщение агента «готово» не является доказательством. Мы проверяем diff, тесты, поведение приложения и соответствие спецификации.

## Результат приложения

К концу маршрута приложение должно поддерживать:

- каталог услуг;
- профили мастеров;
- рабочие графики, перерывы, отпуска и блокировки;
- вычисление свободных слотов;
- регистрацию и аутентификацию клиентов;
- бронирование и отмену визита;
- защиту от двойного бронирования;
- кабинет клиента;
- расписание мастера;
- административный интерфейс;
- email-уведомления и напоминания;
- JSON API, описанный через TypeSpec/OpenAPI;
- автоматические тесты, CI/CD и production deployment.

В MVP не входят оплата, сеть филиалов, программа лояльности, мобильное приложение и AI-рекомендации причёсок.

## Исходный стек

- Ruby 4.0.x;
- Rails 8.1.x;
- PostgreSQL 18.x;
- Hotwire: Turbo и Stimulus;
- ERB, Propshaft и Importmap;
- Active Job и Solid Queue;
- Action Mailer;
- Active Storage;
- Minitest, Capybara и Rails System Tests;
- TypeSpec с генерацией OpenAPI 3.1;
- Docker и Kamal;
- GitHub Actions или другой доступный CI.

Перед инициализацией приложения фиксируем точные версии и проверяем совместимость зависимостей.

## Модуль 0. Базовая модель AI-разработки

### Концепции

- выбор модели и уровень reasoning;
- локальные и облачные модели;
- ассистенты и экономика «цена/качество»;
- context engineering;
- планирование и исполнение;
- устройство агента: loop, harness, tools и MCP;
- память и `AGENTS.md`;
- безопасность и контроль разрешений.

### Практика на барбершопе

1. Инициализировать Git-репозиторий.
2. Зафиксировать версии Ruby, Rails, PostgreSQL, Node и Docker.
3. Сравнить ответы моделей на задачу «спроектировать систему записи к мастеру».
4. Выполнить одну задачу с плохим контекстом и затем с подготовленным контекстом.
5. Разделить запрос на фазы исследования, планирования, реализации и проверки.
6. Создать первый `AGENTS.md`.
7. Настроить безопасные границы: разрешённые команды, секреты и destructive actions.
8. На реальных вызовах разобрать разницу между встроенным инструментом, shell-командой и MCP-сервисом.

### Артефакты

- `AGENTS.md`;
- `docs/learning/00-ai-development-basics.md`;
- журнал экспериментов с контекстом;
- зафиксированные версии инструментов.

### Проверка понимания

Нужно уметь объяснить:

- чем модель отличается от агента и его harness;
- зачем агенту tools;
- когда нужен MCP;
- почему длинный запрос не равен хорошему контексту;
- почему планирование нужно отделять от исполнения;
- что следует хранить в `AGENTS.md`, а что не следует;
- какие действия агент не должен выполнять без разрешения.

## Модуль 1. Spec Driven Development и онтология

### Концепции

- верификация результата работы агента;
- skills и их жизненный цикл;
- Spec Driven Development;
- ADR, PDR и поддержание инженерных артефактов;
- онтология проекта: сущности, связи, состояния и процессы.

### Практика на барбершопе

1. Описать пользователей и границы MVP.
2. Сформулировать user stories и проверяемые acceptance criteria.
3. Построить словарь предметной области.
4. Описать сущности и связи.
5. Формализовать жизненный цикл записи.
6. Зафиксировать бизнес-инварианты.
7. Принять ключевые архитектурные решения через ADR.
8. Описать публичный API в TypeSpec до реализации контроллеров.
9. Создать или подключить первый повторяемый skill для проектного workflow.

### Начальная предметная модель

```text
User
├── role: client | barber | admin
└── BarberProfile

Service
├── name
├── duration_minutes
└── price_cents

BarberService
├── barber
└── service

WorkingPeriod
├── barber
├── weekday
├── starts_at
└── ends_at

TimeOff
├── barber
├── starts_at
└── ends_at

Appointment
├── client
├── barber
├── service
├── starts_at
├── ends_at
├── status
├── price_cents_snapshot
└── duration_minutes_snapshot
```

### Основные инварианты

- Мастер должен оказывать выбранную услугу.
- Запись должна полностью попадать в рабочее время.
- Активные записи одного мастера не должны пересекаться.
- Время хранится в UTC и отображается в часовом поясе салона.
- Цена и длительность сохраняются в записи как snapshot.
- Отменённая запись больше не блокирует время.
- Пересечения защищаются транзакцией и ограничением PostgreSQL, а не только Rails-валидацией.

### Артефакты

- `docs/product-requirements.md`;
- `docs/user-stories.md`;
- `docs/domain-glossary.md`;
- `docs/architecture/`;
- `docs/adr/`;
- `specification/` с TypeSpec и сгенерированным OpenAPI;
- `docs/learning/01-spec-driven-development.md`.

### Проверка понимания

Нужно уметь объяснить разницу между требованием, спецификацией, планом, тестом и реализацией, а также показать, каким автоматическим способом обнаруживается рассинхронизация между ними.

2. Настроить тесты, линтеры и security checks.
3. Реализовать публичный каталог услуг.
4. Добавить seed-данные.
5. Пройти первый полный путь: спецификация → код → тест → review → документация.

### Артефакты

- запускаемое Rails-приложение;
- первый request/system test;
- CI baseline;
- разбор первого agent-assisted изменения.

### Проверка понимания

Нужно самостоятельно определить, какой контекст дать агенту для изменения каталога услуг, и объяснить, почему ему не требуется весь репозиторий или вся история проекта.

## Модуль 4. Расписание и бронирование

### Концепции

- применение SDD к сложной бизнес-логике;
- метанавык обнаружения границ возможностей LLM;
- property-based и табличное мышление;
- конкурентность и инварианты базы данных;
- адаптация архитектуры под надёжную агентную работу.

### Практика на барбершопе

1. Реализовать графики, перерывы и `TimeOff`.
2. Создать чистую операцию вычисления доступности:

   ```ruby
   Availability::FindSlots.call(barber:, service:, date:)
   ```

3. Покрыть граничные случаи табличными тестами.
4. Создать операцию бронирования:

   ```ruby
   Appointments::Book.call(...)
   ```

5. Реализовать транзакционную защиту от двойного бронирования.
6. Воспроизвести конкурентный запрос тестом.
7. Сравнить несколько предложенных агентом алгоритмов и выбрать решение на основе инвариантов и измерений.

### Проверка понимания

Нужно без помощи агента перечислить граничные случаи алгоритма, объяснить источник race condition и показать, почему обычная Rails validation не даёт достаточной гарантии.

## Модуль 6. Паттерны и антипаттерны агентной разработки

### Концепции

- адаптация проекта под агента через структуру кода;
- метанавыки диагностики неудачной работы LLM;
- работа в закрытом контуре;
- типовые антипаттерны агентной разработки.

### Практика на барбершопе

1. Найти компоненты, которые агент регулярно понимает неправильно.
2. Улучшить границы модулей, имена и локальность правил.
3. Сравнить эффект изменения prompt с эффектом изменения архитектуры.
4. Выполнить задачу без внешней сети и определить необходимый локальный контекст.
5. Разобрать антипаттерны:

   - слишком большая задача;
   - реализация без исследования;
   - отсутствие критериев приёмки;
   - доверие непроверенным командам агента;
   - огромный `AGENTS.md`;
   - тесты, повторяющие ошибочную реализацию;
   - бесконтрольный рефакторинг вместе с feature change.

### Проверка понимания

Нужно диагностировать неудачное изменение и определить причину: модель, контекст, инструменты, спецификация, архитектура, проверка или границы задачи.

## Модуль 7. AI в SDLC

### Концепции

- Conventional Commits;
- автоматическая сборка changelog и релизов;
- AI-триаж тикетов;
- CI/CD и deployment через инструменты/MCP;
- интеграция с тикетницей;
- review pull request;
- автоматические отчёты.

### Практика на барбершопе

1. Ввести шаблон issue и формат acceptance criteria.
2. Настроить Conventional Commits.
3. Автоматизировать changelog.
4. Реализовать AI-триаж учебного набора тикетов.
5. Настроить pipeline:

   ```text
   TypeSpec compile
         ↓
   RuboCop + Brakeman + Bundler Audit
         ↓
   Unit + Request tests
         ↓
   System tests
         ↓
   Docker build
         ↓
   Deploy staging
   ```

6. Подготовить автоматическое PR review и итоговый отчёт.
7. Развернуть staging через Kamal или выбранный PaaS.

### Проверка понимания

Нужно провести одну задачу от issue до staging и показать, какие проверки выполнялись автоматически, а какие решения остались за человеком.

## Модуль 8. Оркестрация субагентов

### Концепции

- read-only Reviewer;
- pipeline `Coder → Reviewer → Summarizer`;
- контракт роли: цель, формат и границы;
- выбор модели под роль;
- fan-out параллельных ревьюеров;
- защита от каскада галлюцинаций;
- наблюдаемость передач;
- rule-based оценка на стыках.

### Практика на барбершопе

1. Описать контракт каждой роли.
2. Выполнить одно изменение через последовательный pipeline.
3. Параллельно проверить его ревьюерами по направлениям:

   - безопасность;
   - бизнес-логика;
   - производительность;
   - Rails conventions;
   - тестовое покрытие.

4. Передать результаты агенту-синтезатору.
5. Требовать от каждого замечания ссылку на код, тест, спецификацию или воспроизводимый сценарий.
6. Логировать вход, выход, длительность и результат каждого этапа.
7. Добавить rule-based gate на формат передачи.

### Проверка понимания

Нужно объяснить, почему несколько агентов не гарантируют лучший результат, где возникает каскад галлюцинаций и как контракт передачи снижает этот риск.

## Модуль 9. Работа с legacy-кодом

К этому моменту собственный проект уже содержит историю решений и подходит для безопасного упражнения с legacy.

### Концепции

- анализ существующего проекта;
- погружение AI в структуру кодовой базы;
- characterization tests;
- безопасный рефакторинг;
- постепенное внедрение AI в существующий процесс.

### Практика на барбершопе

1. Выбрать реально усложнившийся участок, не создавая искусственно плохой код.
2. Попросить агента построить карту потока данных и зависимостей.
3. Проверить карту вручную по коду.
4. Добавить characterization tests.
5. Разделить рефакторинг на небольшие изменения без смены поведения.
6. Сравнить поведение, тесты и производительность до и после.
7. Обновить ADR и документацию.

### Проверка понимания

Нужно доказать сохранение поведения и объяснить, почему рефакторинг нельзя считать безопасным только на основании визуально более чистого кода.

## Definition of Done учебного маршрута

Маршрут завершён, когда:

- приложение выполняет заявленные сценарии;
- двойное бронирование невозможно при конкурентных запросах;
- API соответствует TypeSpec/OpenAPI;
- unit-, request-, integration- и E2E-тесты проходят в CI;
- security checks не находят критических проблем;
- production разворачивается повторяемой процедурой;
- документация соответствует коду;
- для каждой концепции курса есть практический пример в проекте;
- учащийся может объяснить концепции без пересказа ответа AI;
- учащийся умеет определить, когда ответ агента требует дополнительной проверки;
- новый агент способен разобраться в проекте через код, `AGENTS.md`, спецификации, ADR и тесты.
